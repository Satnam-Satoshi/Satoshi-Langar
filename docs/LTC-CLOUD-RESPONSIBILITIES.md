# Agent Sangat: cloud operating responsibilities

Human owner: the founder. This document assigns software responsibilities; it does not claim that conversational agents remain running after a chat ends.

## Current verified state — November 4, 2026

The cloud publisher completed the November 4 edition without desktop execution. GitHub history showed no scheduled events on November 3 or 4; manual cloud runs do not prove scheduled operation. Live Vercel data functions work independently of the Mac. Daily cloud social creation remains disabled. Existing Buffer queues are delivered by Buffer.

## Responsibility and authority

| Worker | Mission and sources | Permissions and memory | Failure / escalation |
| --- | --- | --- | --- |
| Research | Collect supported primary project, policy, issuer and network sources | Read sources; dated source observations only | Record source gaps; never invent news or treat observation date as publication date |
| Data quality | Validate prices, network, holdings, distribution and Morpho | Validate observations and provenance; no publishing | Withhold stale values; retain issuer dates and unknown baselines |
| Editor | Prepare daily issue and source desk from validated observations | Allowed data paths only; immutable past editions | No source-backed news means an honestly labelled checkpoint, not fabricated reporting |
| Graphics | Render dated charts and edition artwork from accepted data | Generated public assets; no unsupported claims | Fail validation if graphic and edition dates disagree |
| Publisher | Build, test, stage, verify, promote and checkpoint | Existing protected credentials, exact code pin, fenced private ledger | One writer; unknown effects hold publication; preserve last verified public release |
| Social | Prepare distinct story campaigns and relevant verified mentions | Existing channel allowlist and social ledger | Remains disabled until independent acceptance; never duplicate queued posts |
| Watchdog | Detect missing daily publication on both domains | Proposed separate cloud observer; workflow dispatch only | Not deployed: needs least-privilege authorization, authoritative pause adapter and dispatch-race design |
| Recovery | Verify remote outcomes and preserve evidence | Readback first; existing reviewed recovery controls | Never blindly repeat an unknown mutation or erase incident history |

All workers inherit the founder's emergency stop. Protected publication gates and private ledger pause controls override schedules. Credentials never belong in task memory, logs or articles. Audit records must retain source dates, code/build hashes, external operation identities, verification results and unresolved gaps.

## Layered reliability

1. Existing GitHub scheduler: morning attempts plus afternoon/evening catch-up. Verified same-day admission is a no-op; additional schedules must not produce duplicate editions.
2. Independent cloud trigger: Vercel Cron is the proposed existing-provider fallback. It must observe both domains, pause policy and active runs before requesting the same publisher. It must never become a second publisher.
3. Fault handling: bounded retries only for safe transient reads. Mutations retain durable intents and exact identity verification. A network error is not evidence of non-application.
4. Recovery: current incident records stay private and immutable. Ledger growth must be addressed with a reviewed archive migration before the storage limit; no ad-hoc deletion.
5. Monitoring: a missed deadline, stale domains, held lease or failed run requires an alert. Structured logs alone are not an alert delivery system; an independently tested notification destination is still required.

## Acceptance before claiming autonomy

- New code and scheduler changes reviewed, tested and pinned; protected-main merge approved.
- Same-day reruns prove no duplicate publication or provider effects.
- Next-day real scheduled run publishes a fresh edition on both domains and saves a private checkpoint.
- Simulated missed GitHub event triggers the independent observer; pause and active-run cases never dispatch publication effects.
- Provider read outage, lost write acknowledgement and ambiguous remote outcome tests remain safe.
- Seven consecutive daily runs measured for deadline, freshness and recovery. This is evidence of reliability, not a guarantee of zero failures.
- Social and newsletter activation each have separate end-to-end acceptance; website success does not prove either service.

No part of this design requires a Mac-hosted server, local cron, browser session or Codex heartbeat for routine execution. Proposed components are not active until deployed and verified.
