## Proposed integration plan

1. **Credited discovery directory.** Publish concise independent summaries with links to the official project, repository, license and a checked date. Use status labels such as source available, prototype and needs review. Separate “learn about this project” from a donation destination. Do not duplicate receiving addresses or create a pooled funding process.
2. **Editorial source drawer.** Give LTC articles a visible claim ledger: claim, exact supporting source, effective date, collector observation time and editor classification. Retrieval can locate evidence; generation cannot convert missing evidence into a verified statement. Maintain dated snapshots and corrections. Begin with the existing approved sources; any additional adapter follows the source-method review gate.
3. **Independent read-only LRK pilot.** Choose three clearly defined observations rather than a dashboard of thousands of metrics. First inspect its published schema and public responses; compare block height/hash with an independent Litecoin source. Confirm denomination, time windows, reorg handling and MWEB scope. Retain raw evidence and provenance. Stop publication on stale/malformed data. The README's MCP endpoint is `mcp.bitview.space`, which does not itself prove a Litecoin-specific namespace: chain identity must be checked before any future connection. No MCP connection was created during research.
4. **Project funding visibility.** Link to the Foundation's own project destinations; independently record proposal, active development, released and independently reviewed as separate states. If a later approved feed is built, omit private applications, donor identities and contact details. The donation repo warns that application detail URLs are currently obscured rather than authenticated: do not collect or republish those records.
5. **Wallet research in a separate environment.** Only after separate authority, license clearance and threat modeling, evaluate fixed revisions using test fixtures/regtest and no real value. Review key generation/storage, backups, MWEB state separation, PSBT extraction and peer omission behavior. Document which tests are developer-reported and which we reproduce. An audited library would still not audit our app. No private keys, seed phrases or transaction actions are part of editorial onboarding.

Acceptance for the first real integration: exact revision/rights recorded, public API contract verified, source budget and privacy behavior documented, reproducible evidence checks passing, rollback available, and deployment explicitly authorized under the project process. These are proposed milestones, not completed implementation claims.
