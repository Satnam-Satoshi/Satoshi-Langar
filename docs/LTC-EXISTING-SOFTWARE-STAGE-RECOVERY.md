# Existing software-stage recovery

This manual path is for one reviewed, already-created candidate. It does not call the daily publisher, rerun software staging, rebuild, or upload the artifact archive again. A successful metadata or sampled-byte diagnostic is not promotion authority.

## Separate identities

- **Artifact source and implementation** identify the original immutable UI/API package.
- **Controller source and implementation** identify the audited recovery code. They must match the accepted source branch and protected implementation pin.
- **Operator workflow head** identifies the exact main-branch workflow that dispatches recovery.
- **Original run and fence** remain attached to the original stage intent and archived receipts. Recovery must not impersonate the failed runner or relabel its history.

## Preflight before any state change

1. The original workflow must be a terminal failed first-party software release. Read its authoritative run metadata.
2. The reviewed journal snapshot, old lease, original review/context, prior release and every archived receipt must match exactly. Review validity is admission and first-promotion scoped.
3. Restore only the verified manifest bundle and selected original-review bundle(s), plus the previous release summary. Do not restore or regenerate the 42-part artifact archive.
4. Verify current project policy, previous production pointers, unique candidate operation metadata, every protected manifest record and all four API contracts.
5. Only after these read-only checks may the reviewed core confirm the original stage and acquire its explicitly authorized new fenced claim. Preserve prior daily publication time and all historical safety evidence.

## Controlled completion

The mutation adapter admits only promotion of the existing candidate, or the bounded reviewed rollback. It rechecks live ownership, expiry, holds, exact intent and historical stage after awaited reads immediately before an external mutation. No deploy command is admitted. An ambiguous provider write must remain unresolved; never retry it blindly.

After successful promotion, verify both public domains, preserved static records and all APIs. Persist and read back the completed release checkpoint before releasing the recovery lease. A failed check is not a successful publication. The daily schedule and separate one-time software gates must not be modified by this workflow.

## Operator sequencing

Run focused and complete controller tests, independently review the combined source, and obtain exact-head CI before adoption. Install the reviewed manual workflow on main without replacing daily/social jobs. Coordinate controller acceptance and migration pins while preserving the original artifact identity. Prepare a fresh, bounded recovery review against the current snapshot and final operator/controller commits; do not reuse an expired first-promotion review. Protected control changes require their applicable user authorization.

Dispatch the reviewed recovery once through the existing protected environment. Capture the actual run ID. If withheld, inspect its allowlisted failure phase and fresh journal before deciding another action. Do not clear a retained lease, change history, or create another deployment to hide the failure.
