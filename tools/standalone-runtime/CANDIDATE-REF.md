# Dormant cooperative candidate-ref executor

Source implementation and synthetic tests only. No GitHub/Firestore services, credentials, branch update, CI hook, preview or publication was exercised. Default network and mutation switches are false. `npm start` remains disabled.

## Fixed operation and sequence

`createGitHubCandidateRef` in `src/adapters/github-candidate-ref.mjs` accepts `github`, independently retained `pins` (the complete candidate observer's exact schema), `claim:{owner,fence}`, `journal`, `loadApproval`, `clock`, and explicit opt-in `networkEnabled` / `refUpdateEnabled`. `github.branch` must be the **existing** `agent/standalone-candidate` branch in the fixed canonical repository. Missing branch is not created. All candidate Git objects must already exist; this module does not upload blobs/trees/commits.

`advance()` invokes the actual complete-tree/data-only observer, not a supplied eligible flag. This checks pinned commit/tree identity, single baseline parent, append-only issue registry and four exact new artifact blobs including the inert reader profile. A fresh independently loaded approval must bind the exact identity, reference, review digest, time window, `branchTriggeredAutomationReviewed:true`, `productionHooksBlocked:true`, and exact `hookPolicySha256`. These are assertions from the **independently authenticated approval/configuration loader**, not authentication generated by this module. Hooks must be inspected and production safeguards maintained outside this code. Approval covers potential CI and automatic preview/deployment hooks and their quota/cost consequences, not merely this function's HTTP requests.

The concrete journal below supplies current owner/fence/lease/stop and the matching reviewed hook-policy digest. The executor verifies baseline, persists an intent with exact readback, rechecks control and full intent, then rereads the baseline immediately before PATCH. Every effect is preceded by finite monotonic clock, approval, observation and lease expiry checks. PATCH is only:

```
PATCH https://api.github.com/repos/Satnam-Satoshi/Satoshi-Langar/git/refs/heads/agent/standalone-candidate
{"sha":"<exact candidate commit>","force":false}
```

The bounded response and a separate GET must identify the exact candidate. The journal then becomes observed. `reconcile()` is GET-only and remains available after original approval/lease expiry; it never changes the journal or retries PATCH. A prior intent, including an unknown request outcome or unknown journal commit, always causes read-only observation on restart. Baseline still present is **not** permission to retry. Same candidate observed establishes only the current ref value associated with the durable intent, not proof this request caused it. An unresolved intent blocks another new identity on that branch until a separately reviewed reconciliation procedure exists.

`createPreview()` and `promote()` always hold. No final editorial, build, deployment or publication authority is returned. Branch mutation can nevertheless trigger configured provider hooks; absence of a direct Vercel call is not absence of a deployment side effect.

## Concrete durable journal

`createFirestoreCandidateRefJournal` in `src/firestore-candidate-ref-journal.mjs` accepts the injected official `Firestore` constructor, exact project/database, the executor's `identity()` result and claim, independently pinned `hookPolicySha256`, clock, and `mutationEnabled:false` by default. Its SDK constructor may execute injected code; it is not a sandbox. No ambient emulator is permitted. It uses only fixed paths:

- `newsroomPrivateCandidateRefsV1/inventory`
- `newsroomPrivateCandidateRefIntentsV1/<canonical identity SHA256>`
- the existing standalone global controller document.

The inventory **must already exist**, independently initialized and migrated. Exact fields are schemaVersion1, generation `standalone-candidate-ref-inventory-v1`, initialized true, canonical repository/branch, writerMode `exclusive-cooperative`, hookPolicySha256, positive safe revision and claims. Each claim is `{version:1|2,stateSha256}`. No bootstrap or history reset is supplied. An unclaimed key with an absent row may report version0/null; a claimed missing/zero/mismatched row or orphan always holds. Atomic first CAS allocates claim+intent. Atomic second CAS preserves immutable intent fields and changes only phase. The inventory hash/version is updated with each row, detecting row-only rollback. Capacity100 holds rather than trimming history. Another unresolved branch intent blocks a new key. Transaction callbacks contain no HTTP effects; SDK retries cannot repeat PATCH.

The current global owner/fence/lease/stop is read in the same transaction as writes. Exact committed state is read back before reporting CAS success. Unknown commit latches this instance to reads only. Whole-store/root rollback, dishonest injected SDK/HTTP functions, IAM compromise, and uncontrolled writers are external trust limits. SDK installation, credentials, initialization/migration, lease orchestration and real deployment configuration remain unimplemented activation steps.

## Not a hard provider CAS

GitHub REST accepts only the new SHA and `force`; it has no expected-old-SHA condition here. Fast-forward enforcement is useful but is not exact compare-and-swap. There is an unavoidable cooperative interval between the final ref/control reads and HTTP execution. This code cannot fence a malicious writer or atomically coordinate GitHub with Firestore. Production use needs a separately reviewed single-writer/hook posture and owner activation. No guard settings are altered by this code.

Official endpoint contract checked during implementation: [GitHub update a reference](https://docs.github.com/en/rest/git/refs#update-a-reference), API version `2026-03-10`. HTTP200 acknowledges the update, not deployment or publication. Error/timeout/redirect/oversized responses are held without automatic retries.
