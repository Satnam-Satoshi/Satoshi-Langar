# Dormant monitoring and scheduler contract

The pure `evaluateRunHealth` monitor classifies an independently authenticated durable run observation as pending, running, held, failed, stalled, late, missed, unknown, or completed. It never retries work, publishes, repairs state, or sends an alert. Alert IDs are deterministic for downstream durable deduplication; `deliveryVerified:false` is deliberate until an approved alert transport confirms delivery. No monitoring resource or notification subscription exists yet.

Expected run identity and scheduled/deadline times come from trusted deployment scheduling, not model output or a story manifest. The observation's `authenticated:true` is an adapter trust assertion, not authentication performed by this module. Production must bind it to a direct authorized datastore read. The monitor rejects observations older than one minute, invalid/future clocks and unrelated run identities. A verified historical completion does not claim source freshness or current site availability; those need separate checks.

Candidate scheduler configuration, NOT deployed: one Cloud Scheduler trigger, timezone America/New_York, preserving the existing single daily producer timing rather than adding a second email publisher. Exact cron, target job/service identity, timeout and retry policy need reviewed cutover. Derive immutable issue/revision/run identity from the original scheduled event; repeated or late delivery must consult the canonical migrated state, not create another publication. A regional scheduled trigger is not proof of job execution or success. Never retry an uncertain publication solely because an alert fires.

Broad pipeline gaps still open: genuine multi-source article production; semantic review policy; renderer/PDF/browser QA; private evidence/outbox; exact preview/publication/provider reconciliation; approved email subscription flow; per-story public assets, tag verification and direct social execution; real alert delivery and cost monitoring. Source-level tests do not establish autonomous operation. Model API use is optional and must have approved service/secret/budget before calls; ChatGPT/MCP is not a runtime prerequisite.
