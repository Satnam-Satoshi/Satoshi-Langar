# Dormant canonical consumer inbox

`createFirestoreConsumerInbox({Firestore, expectedProjectId, expectedDatabaseId, config, claim, clock, mutationEnabled:false})` implements `reserve(canonicalEvent)`, `accept(canonicalEvent)`, and `readConsumerReceipt(exactBridgeRequest)`. It imports no SDK or credentials. The independently supplied reviewed Firestore SDK/service identity is the authentication boundary. Synthetic SDK tests do not prove deployed IAM or durability.

Config is exactly `{jobName, expectedEtag, sourceCommit, jobImageSha256}`; claim is `{owner,fence}`. The existing root `newsroomPrivateConsumerV1/inventory` must have schemaVersion1, generation `standalone-consumer-v1`, initialized:true, positive revision, configSha256 of canonical config, and claims mapping scheduler keys to SHA256 of canonical `{event,config}`. There is no root initialization, reset, migration, pruning or configuration rollover method. Initializing this root without auditing existing work would be unsafe and is not authorized by this source.

## Concrete lifecycle

Reserve reads the existing controller and exact inventory-backed scheduler dispatch intent transactionally, within the canonical event window. For a genuinely unclaimed key and absent inbox row, it atomically appends the retained inventory claim and creates the reserved inbox. Known missing rows, unindexed rows, same-key divergent source/image/event identities, counter exhaustion, missing canonical state and expired ownership hold. Reservations retain original dates and full immutable event/config bindings.

Accept requires that reservation and the same live controller owner/fence. It reads the exact inventory-backed Cloud Run journal version2 operation-known record in the transaction. The operation is taken from the retained transport response, never invented before Cloud Run responds or supplied as an arbitrary operation argument. Pending/unknown transport outcomes hold. Acceptance atomically changes the reserved inbox to accepted, storing owner/fence and canonical receipt. Both first transitions require fresh schedule window before writes and exact committed readback. Transaction callbacks perform only store operations, no HTTP, models or publishing. An uncertain transaction/readback latches further writes; fresh readers can reconcile without reissuing effects. Exact replay does not write or create another job. Results explicitly return performWork:false and workAuthorized:false; newlyClaimed describes only the first durable acceptance transition. Neither replay nor reconciliation authorizes execution or resume of preparation. Unknown writes throw and cannot be interpreted as a new work claim. Worker execution/resume remains a separate independently fenced contract.

`createFirestoreConsumerBridge({store,bridge})` binds the actual fixed-store reader to the existing schedule bridge and rejects an overriding readConsumerReceipt callback. It also checks source/job/etag agreement. Reader transactions validate retained inventory, exact request/source, original event, image-config digest and receipt bytes. Accepted historic receipts remain readable after the acceptance window; their acceptedAt is not refreshed. New observedAt describes only the store read. Receipt means durable acceptance of work, **not execution success, verified facts, rendered output, or publication**.

## Explicit remaining prerequisites

The configured image SHA is an authorized immutable pin, **not actual container-image or execution attestation**. This module cannot establish which image is running from a caller's config, or prove that a running Cloud Run execution belongs to the observed operation. Trusted deployment configuration/runtime identity binding and its independent observation remain required before operational acceptance. No job arguments/overrides are injected; the entrypoint must explicitly read the canonical reserved work, not infer a date from wall time. The module now supplies the reservation/receipt writer and reader, but the actual container entrypoint, authorized source preparation worker, runtime operation/execution association, IAM, existing-root migration/initialization and service wiring remain unimplemented here. No schedules or services are activated.

Root inventory holds at 1000 retained claims rather than silently trimming history. Configuration change needs a separately reviewed migration preserving history. A single row holds acceptance and immutable identity atomically, not a parallel ledger. Firestore multi-document transactions supply cooperative storage serialization; they do not fence external provider effects or attest runtime code.

Tests use only synthetic in-memory SDK snapshots and mocked provider GET responses, including reserve→accept→actual bridge reconciliation, replay, unknown commits, lost rows, image substitution, deadline crossing, controller ownership, counter bounds, readback corruption and disabled mode.
