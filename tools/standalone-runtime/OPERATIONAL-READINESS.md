# Standalone operational readiness: blocked, not activated

The container has an offline synthetic preparation → real local rendering → mocked private archive → fresh-process readback test. It does not depend on ChatGPT or a desktop to execute that test. This is not proof that real provider credentials, semantic review, publication, marketing or unattended scheduling work. Default startup is disabled. A syntactically valid configuration, matching digest or general autonomy request is not authenticated operational approval.

## Engineering gates, not questions to delegate to the owner

1. Bind retained source bytes to independent factual review and source-specific freshness/novelty policy. Lexical quotation fidelity and a reviewer-reference allowlist are not semantic truth or proof of reviewer identity. Unknown, historical and unavailable observations remain labeled; preparation produces drafts, not publishable claims.
2. Compose reviewed source/image provenance, authenticated runtime identity, approval records, canonical inventory and live stop/lease checks. Environment variables and provider resource metadata are observations, not signed execution attestation. Configuration validation must not manufacture these records.
3. Complete the standalone candidate write/data admission and release path: exact source/data tree, immutable archives, actual application/content/visual verification, preview QA, durable final QA archive, controlled promotion, both-domain byte verification and durable publication record. A provider acknowledgment alone is never completion. The dormant adapters now compose exact candidate creation, preview, final pre-promotion QA archival, controlled promotion and two-domain observation archival in synthetic tests. All effects remain disabled by default; real credentials, enrolled authority, runtime admission and provider compatibility are not established. Missing archive/control gates hold before promotion, and API acknowledgment is not durable public completion. Unknown candidate-ref intents remain read-only reconciliation holds rather than automatically resolved claims.
4. Complete marketing hosting and mutation orchestration using the migrated private ledger, verified published story identities and source/tag evidence. Read-only Buffer responses or stable paired reads do not establish ownership, deleted-history absence, authorization or an atomic queue snapshot. The dormant generator now checkpoints the complete append-only backlog before private reservation. A separate default-disabled Buffer executor composes exact action approval, indexed durable intent, provider response validation and read-only restart reconciliation in synthetic tests. Lost provider acknowledgments never trigger another create; a retained provider ID is not public delivery proof. The backlog cursor is deliberately not advanced merely by preparing a batch. Existing historical-ledger migration, authenticated queue/account evidence, public hosting/visual verification, complete request-budget accounting and actual provider acceptance remain necessary. The queue loader remains incomplete/non-atomic and account publishing capacity remains unknown; action-specific provider enforcement is not invented capacity. Typed rejections and unknown intents are retained rather than automatically cleared. No real Buffer draft, schedule or post has been created by these tests.
5. Install an operational scheduler and alert path only after end-to-end testing. Container/job success is not an edition, delivered alert or sent campaign. Unsupported alert reasons remain explicit holds until reviewed mappings exist.

## Owner/admin decisions needed for a concrete reviewed rollout

These should be requested with exact project, recipient, permissions, cost and consequences once the corresponding implementation is ready. This document grants none of them.

- Select and approve the actual billing linkage, service terms, region, resource plan and cost controls for the cloud project. A planning budget is not billing activation or a universal hard spend cap.
- Approve least-privilege runtime/deployer/Scheduler service identities and exact Secret Manager access. No ambient connected-app credential may be extracted or silently reused for the standalone worker.
- Approve a founder-owned direct Drive OAuth application, offline permission and encrypted token storage for the exact archive destination. Use the narrow per-file scope only where the real folder workflow supports it. Verify OAuth publishing/audience status, refresh-token longevity/revocation behavior, owner-only readback and recovery. An upload once does not prove unattended access. Observed owner-only access is non-atomic and retention is not WORM.
- Review canonical-history migration and retirement of competing writers before a single production cutover. Preserve issued editions, pending attempts, queued posts, drafts, reserved slots and founder-email deduplication. Never initialize an empty ledger to avoid reconciliation. Existing pause/stop rules take precedence over copied enabled flags.
- Approve exact Vercel project access/build settings and the first reviewed publication scope. Prior expired revision permissions are not reusable; a test/archive permission is not recurring production authorization.
- Separately approve the risk and storage of a direct Buffer account-wide credential for the exact project channels. Fixed code targets do not make the credential itself narrowly scoped.
- Verify the existing Brevo account/sender and approve the owner-alert destination and credential use. Subscriber double opt-in, unsubscribe/suppression and feed activation are separate from operational alerts or the founder's daily email.

## Live acceptance evidence required before claiming autonomy

- Real service identity, source-to-image provenance and approval loader bind the running worker to the reviewed artifact.
- Real initialized stores preserve canonical history and reject missing/reset/rolled-back rows within the documented trust model.
- Real Drive archive bytes, versions and access observations survive process loss; unknown uploads are not retried blindly.
- A bounded independently reviewed edition passes freshness checks through render, queue, QA and release; stale evidence holds rather than being relabeled current.
- One exact release is independently verified on both domains and recorded durably. Same-day revision semantics must be implemented explicitly; the prototype date/target/phase conflict must not be loosened to force a correction.
- Duplicate triggers, crashes, uncertain provider outcomes, quota failures and revoked credentials do not create duplicate editions, founder emails or social posts. Stop behavior and owner alert delivery are observed, not inferred from API acceptance.
- Rollback/reconciliation is tested without overwriting a newer external deployment. Cooperative checks do not provide provider-enforced fencing across independent writers.

Until these gates pass, report the particular tested layer and remaining gap. Do not describe the whole website, source ecosystem or marketing operation as refreshed/autonomous because one draft, container or fixture succeeded.

## Optional model data boundary

No model provider is activated by these modules. Before adding a research or editorial model endpoint, independently verify the actual account, billing tier, region, retention/training terms and approved input scope. A free allowance or existing account is not approval to transmit private editorial drafts, subscriber records or credentials. Keep credentials out of model inputs under all tiers; minimize other data and require the applicable sharing approval. A paid tier must not be assumed to mean zero logging or retention. Synthetic local tests do not establish a provider's privacy configuration.

## Scheduler and task retry boundary

Treat scheduler delivery, manual invocations and worker/task retries as potentially repeated. A run header, retry setting or scheduler timestamp is not authenticated caller identity and is not an exactly-once guarantee. Before activation, independently verify the actual Scheduler caller authentication and Cloud Run retry configuration. Preserve durable per-edition/per-post intent and unknown-outcome reconciliation across process loss, lost acknowledgments and new invocations; never clear uncertainty or deduplicate solely by an unauthenticated header. Existing synthetic idempotency tests do not prove the deployed retry/IAM configuration.
