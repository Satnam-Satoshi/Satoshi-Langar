# Minimal cloud editorial integration (design, not deployed)

## Decision
Reuse the **existing sole GitHub Actions publisher**, existing collectors, current feature schema and private evidence archive. Do not introduce another website publisher or a second scheduler that can race releases. Add source-grounded authoring and independent review between selected source collection and first feature creation. The same exact admitted feature JSON feeds the website, PDF and social campaign. Do not reconstruct stories independently in three channels.

The smallest code insertion is in `prepareObservations` in `scripts/cloud-ltc-release.mjs`: after `archive-ltc-ecosystem.mjs` chooses `ecosystem-selected.json`, before `prepare-ltc-daily-features.mjs --publish`. This is a proposed change requiring digest acceptance and dry-run; no insertion has been made.

### Why not a new scheduled writer first?
The repository already has immutable dated feature files and same-day report selection. A separate writer changing source between admission and deploy causes a source-head race. Inline preparation uses the selected report, the same source checkout and current sole-writer protections. It also avoids dependence on a live dot turn, Mac browser, native cron or a new GitHub PAT. The publisher must renew/revalidate its lease during the extra bounded work; if its implementation cannot do this, stage editorial preparation before lease acquisition and bind the exact staged content digest at admission instead. Do not simply lengthen a lease without reviewing crash reconciliation.

## Required hosted capability
Use a provider-supported structured-output LLM API from the cloud runner, through one reviewed wrapper with bounded timeouts and an explicit spending cap. It needs a cloud-held API credential or an already approved managed-model integration. No such capability/key has been verified for this repository, so model calls are not implemented or enabled here. Do not use a Mac CLI login, browser cookie, personal Coinbase connection, public build variable, or new persistent credential as a shortcut. Configure any additional credential via the authorized managed secret workflow; never put it in a PR or logs. Existing GitHub/Google/Vercel access is not evidence of model API access.

The writer and reviewer may be two separate calls to the same approved model provider, but must have separate contexts. The reviewer receives source evidence and draft only, not a persuasive writer narrative or writer's own approval. Record provider request/model/version identifiers privately. AI review is not a guarantee of truth; escalations below still apply.

## Actual daily sequence, all cloud-side
1. Existing scheduled workflow obtains a run identity and checks the publication ledger. An active, completed, uncertain or held release is never duplicated.
2. Existing collectors save raw responses plus `*.receipt.json` outside the repository. `archiveEcosystemReport` picks the day's immutable report. **Use its selected event hashes**, not a newly fetched body's hash on a same-day retry.
3. Evidence resolver locates full response bytes by SHA256 and verified URL in that run or the private immutable recovery archive. Reused community/builder/policy events need their corresponding raw collector archives. An ecosystem index receipt is not a substitute for an article body. If an event has no recoverable matching body, mark it unavailable for substantive reporting; do not ask a model to fill the gap.
4. Extract readable main content with a tested parser; save raw hash plus extracted-text hash/parser version. Strip script/style/navigation, bound size and preserve content. Publisher text is **untrusted data**, never instructions. Unknown encodings, CAPTCHA pages, access-denied pages, paywalls and ambiguous dates withhold. Follow configured URL/redirect rules; no model-selected arbitrary URL fetching.
5. Rank only genuinely dated, unreported candidates. Prefer up to 3 strong stories over 8 empty paragraphs. Context from older stories is clearly labeled. A verified no-new-story day is allowed. Keep source failures visible. mNAV/Bitbo stay manual/licensed unless authorization is independently established. X discovery is not full timeline coverage; use verified exact posts where available and state omissions.
6. Writer emits the existing feature JSON **and a private claim ledger**. Each material factual statement maps to exact source IDs, source passages/offsets and original publication/event/observation dates. Each numerical value has unit, currency, period/as-of date and named source. A source statement is attributed, not presented as independently audited fact.
7. Deterministic checks validate schema, dates, source identities, evidence hashes, numerical occurrence/unit/date matching, source freshness, citation completeness and permitted output paths. These checks do not prove semantic entailment. Same-name tickers, page changed hashes, search snippets and titles are not enough evidence for launch, partnership, treasury change or institutional adoption.
8. Reviewer independently compares every material claim against archived evidence, then checks the complete prose for uncited claims, unsupported certainty and copying. Reviewer emits per-claim pass/reject plus reasons, required cuts and source coverage gaps. If revision is needed, allow one writer revision and one independent re-review. Timeout, provider outage, budget ceiling, ambiguous evidence or remaining rejected claims => no substantive candidate admitted.
9. Protected runner authenticates the reviewer invocation and binds its approval to the exact feature, evidence and coverage hashes. It applies existing `validateFeatures` plus this draft's `evaluateEditorial`. The model cannot approve a release or alter source registry, gates, branch, credentials, workflow, recipients, file paths or policy.
10. If the exact date already has valid authored content, preserve it and its historical evidence. Do not silently rewrite or replace a published edition. New admitted features are created once using exclusive write. A subsequent release retry reuses the same immutable evidence and feature identity rather than paying to regenerate.
11. Existing publisher builds, tests and promotes through its existing lease, digest, private-state and dual-domain verification. The editor module never calls GitHub merge, Vercel deploy, email or Buffer.
12. Email/PDF and social workers read the verified published edition ID/feature hash. Only those accepted stories receive cover artwork/captions and verified story-specific handles. No separately invented claims. Record their own delivery receipts and idempotency keys.

## Honest fallback
The current generator can remain the fallback ONLY as visibly labeled source-watch/context, never as a reported daily scoop. If already-approved current-date authored features exist, prefer them. Otherwise keep unavailable feeds and the absence of admitted news explicit. A fallback is a dated reading/check record, not proof nothing happened. A failed author/reviewer must not be disguised as “all news covered.” No new marketing campaign should sell a fallback as breaking news. Surface one material coverage notice rather than repeating every collector failure.

## Human escalation (not a daily approval loop)
Eddie authorized routine autonomous news preparation/publication. Routine properly supported public news therefore need not wait for a new approval each morning. Escalate only concrete material exceptions: allegations about identifiable people, confidential/nonpublic information, claims of confirmed partnerships/endorsement unsupported by both sides, paid sponsorship/contract commitments, tax/legal status changes, or financial instructions outside editorial reporting. Keep the rest of the edition moving. Human oversight can also select stories/angles or correct the source registry; it does not require operating Safari.

## Minimal rollout / acceptance
A. Recover the earlier evidence reader if possible, otherwise implement the bounded archive resolver and extraction layer. Wire a real approved hosted model transport. Add writer/reviewer JSON schemas and bounded call wrapper. Do not treat the example prompts as an executable integration.
B. Exercise three offline cases with synthetic data: two valid stories; one substantive story + unavailable feed; no admissible stories. Add adversarial fixtures for injected page instructions, fabricated mainnet claims, unit/date changes, reference-only evidence and modified review bytes.
C. Hosted dry-run with the Mac off: source collection -> body archive -> writer -> reviewer -> gate -> existing feature validator. Verify no deployed writes, no full source bodies in the public repo, no secrets in logs, bounded spend, no duplicate calls after interrupted retry.
D. Integration tests prove existing immutable authored files and report selection survive, ledger/lease checks are not bypassed, existing publisher tests/build pass, and PDF/social consume the same feature identity. Exact current baseline and implementation digest need coordinated acceptance, not an unrelated UI deployment.
E. Enable only the existing sole publisher path. First real edition must independently verify ledger + live dated routes + both homepage edition links; PDF/Buffer each verify their own receipts. Next morning repeat with Mac locked/off. Until this evidence exists, describe the workflow as a tested draft, not autonomous original reporting in production.

## Practical content contract
Per story public: headline, original explanation, why it matters, what remains unproven, dated source links, related internal page links. Avoid price predictions and investment exhortations. Specific coverage: Litecoin Foundation/Core, LitVM and verified builders, LiteDrive/L2, cLTC/Canton (exact relationship scope), wallets/mining/payments, company treasuries, ETF/ETP products. Separate announcements from measured metrics. Keep Bitcoin comparisons meaningful (same dates, units, methodologies) rather than presenting unmatched numbers.
